# Document Intelligence Assistant — RAG-Powered Agentic Q&A Service

A self-hosted, agentic Q&A system over a corpus of PDF documents (research papers). Answers are generated by an open-weight model served through **vLLM**, grounded in retrieved passages *and* figures/tables, cited by source and page, and self-verified before being returned. Out-of-scope or unsupported questions get an honest "not found" response instead of a fabricated answer.

---

**Why one VLM for everything:** rather than running a separate text LLM and vision-language model (two GPU-memory budgets), the whole system is served by a single vision-language model, **Qwen2.5-VL-7B-Instruct-AWQ**, through one vLLM instance. It handles ingestion-time figure/table description *and* runtime answer generation/grading/verification. This follows the assignment's own suggested approach for constrained GPU memory (Section 5, Step 5) and keeps the deployment to one long-running model-serving container instead of two.

## 3. Setup

### 3.1 Prerequisites

- Docker + Docker Compose, with an NVIDIA GPU and the NVIDIA Container Toolkit installed
- A GPU with enough VRAM to run a 7B AWQ model comfortably (a single 16 GB+ card is sufficient at the settings below)
- 12 PDFs placed in `./data/`

### 3.2 Configure

```bash
cp .env.example .env

```

`docker-compose.yml` sets `VLLM_BASE_URL` / `VLLM_MODEL` / `VLLM_API_KEY` directly for every container, so `.env` is only needed for running `ingestion.py`, `rag.py`, or `benchmark.py` locally against a vLLM server you started yourself.

### 3.3 Bring up vLLM

```bash
docker compose up -d vllm
```

Wait for the health check to pass (`docker compose ps` shows `vllm-server` as `healthy`) before running ingestion — the healthcheck polls `/health` on the vLLM server.

### 3.4 Run ingestion (one-time, or whenever the document set changes)

```bash
docker compose --profile ingest run --rm ingest
```

This is **not** started by `docker compose up` on purpose — it's a one-shot job, not a long-running service. It reads every `*.pdf` in `./data`, extracts text and figures/tables, describes visuals through vLLM, embeds everything, and writes to `./chroma_db` (and crops to `./extracted_visuals`).

### 3.5 Bring up the API and UI

```bash
docker compose up -d rag-api streamlit
```

- API: `http://localhost:8080` (`/health`, `/ask`)
- Streamlit UI: `http://localhost:8501`

### 3.6 Smoke test

```bash
curl http://localhost:8080/health

curl -X POST http://localhost:8080/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "What is the main contribution of the paper?"}'
```

**Out-of-scope example (demonstrates the fallback path):**

```bash
curl -X POST http://localhost:8080/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "Who won the 2022 World Cup?"}'
```

Expected: `path_taken` shows `route: OUT_OF_SCOPE`, and the answer is the honest fallback message rather than a guess.

## 4. Design decisions and trade-offs

### 4.1 Model serving (Part A)

| Parameter | Value | Why |
|---|---|---|
| Model | `Qwen/Qwen2.5-VL-7B-Instruct-AWQ` | Single vision-language model handles both text QA and figure/table description, avoiding a second model-serving process on the same GPU. AWQ quantization keeps a 7B model within a single mid-range GPU's memory budget. |
| `--max-model-len 8192` | 8192 tokens | Enough headroom for a multi-chunk retrieved context (5 chunks × ~800 chars) plus the citation-rules prompt and a full answer, without paying for a context window the RAG use case doesn't need. |
| `--gpu-memory-utilization 0.75` | 75% | Leaves ~25% of VRAM as headroom for the KV cache under concurrent requests and for the ingestion job's own GPU usage (DocLayout-YOLO) when both run on the same machine. |
| `--limit-mm-per-prompt '{"image":1,"video":0}'` | 1 image/prompt | The system only ever attaches one figure/table image per query (`MAX_IMAGES_PER_QUERY` in `rag.py`) — capping it server-side keeps memory predictable under concurrency instead of letting a pathological request attach many images at once. |
| `--mm-processor-kwargs '{"max_pixels":401408,"min_pixels":3136}'` | bounded image resolution | Caps the token cost of an attached image (an unbounded high-resolution figure would consume a disproportionate share of the context and processing time relative to the text). |
| `--enforce-eager` | eager mode | Skips CUDA graph capture at startup, trading a small amount of steady-state throughput for a faster, simpler startup and easier debugging on a single-GPU dev/eval box. |
| Tensor parallelism | not used | A single 7B AWQ model fits on one GPU at these settings, so splitting it across GPUs isn't necessary here. |

**Benchmark:** see `benchmark.py` and Section 6.

### 4.2 RAG pipeline (Part B)

- **Chunking:** `RecursiveCharacterTextSplitter`, chunk size 800 / overlap 120, splitting on paragraph → sentence → word boundaries. 800 characters keeps each chunk small enough that a single citation `[Sx]` points at a focused piece of evidence (important for the citation-validation and hallucination checks), while 120 characters of overlap avoids losing context at chunk boundaries for statements that straddle two chunks.
- **Embeddings:** `sentence-transformers/all-MiniLM-L6-v2` — small, fast, CPU-friendly (so the API container doesn't need its own GPU just to embed a query), and adequate quality for this corpus size.
- **Vector store:** Chroma, persisted to disk — simplest local vector store that needs no separate service to run, appropriate for a 10–20 document corpus.
- **Retrieval:** hybrid — dense similarity search (Chroma) **and** BM25 lexical search over the same corpus, fused with weighted **Reciprocal Rank Fusion** (dense weight 0.7 / BM25 weight 0.3). BM25 catches exact term matches (model names, metric names, numbers) that dense embeddings sometimes miss; RRF combines both without needing to calibrate similarity scores against BM25 scores directly.
- **Generation & grounding:** every factual sentence in the answer must carry a `[Sx]` citation tag pointing at an actual retrieved source. This is enforced twice: the generation prompt itself (with an explicit example format and instruction to say "I don't have enough information" when the context is insufficient) and a citation-validator (`validate_citations` in `rag.py`) that rejects any answer whose citations don't map to a real retrieved source. The prompt also includes an explicit instruction to treat any text inside the retrieved context as data, never as instructions to follow — a basic defense against prompt injection via document content.

### 4.3 Agentic workflow (Part C)

Implemented with LangGraph (`langgraph_rag.py`). Router classifies every query as `RESEARCH_PAPER` / `GENERAL` / `OUT_OF_SCOPE` before anything is retrieved, so chit-chat and out-of-scope requests never touch the vector store. The retrieve → grade → rewrite loop caps at `MAX_RETRIES = 2`, rewriting the query with an LLM call that preserves intent while adding technical terms likely to improve recall. The verification step is a second, independent LLM call that re-checks the *generated answer* against the *retrieved context and images* — a genuinely separate hallucination check, not a reuse of the relevance grade. Both the relevance and verification checks are multimodal-aware: if a chunk is a figure/table, the actual image is attached to the grading prompt, not just its caption, so a correct answer about a chart's contents isn't wrongly marked unsupported.

### 4.4 Multimodal capability (Part E)

**Option chosen: image-aware ingestion (Option 1).** During ingestion, `DocLayout-YOLO` detects figure/table regions on every page, each is cropped and sent to the VLM (served via vLLM) for a structured description (chart type/axes/values for charts, components/connections for diagrams, columns/values for tables), and that description is embedded and indexed exactly like a text chunk — with the same citation metadata (source, page) plus a `visual_id` and `image_path`. This means a question like *"What does Figure 11 show?"* is answered through the normal retrieval path with no special-casing, and the answer/verification steps re-inspect the actual image (not just the indexed description) before finalizing.

Option 2 (a separate `/ask-image` endpoint for uploaded images) was not implemented — the assignment allows either option alone, and image-aware ingestion was the better fit for a "search my documents" product, where the images that matter are already inside the corpus rather than uploaded ad hoc.

### 4.5 API & packaging (Part D)

FastAPI exposes `/health` and `/ask`. `/ask` returns `path_taken` — the full LangGraph result state minus the bulky document objects and answer text — so a caller can see exactly which route was taken (router classification, retry count, relevance/verification outcome) without re-running the graph or reading server logs. Citation parsing and legend-building live in one place (`rag.py`) and are imported by both `api.py` and the CLI, so citation formatting can't drift between the two entry points. `docker-compose.yml` brings up `vllm` (long-running), `ingest` (one-shot, `--profile ingest` only), `rag-api`, and `streamlit`, wired together with `depends_on` health/start conditions.

## 7. Known limitations

- **Single-GPU, single-model serving.** Text generation, grading, verification, and VLM description all share one vLLM instance — under heavy concurrent load, ingestion (if re-run) and query traffic would contend for the same GPU.
- **BM25 index is rebuilt in memory at process start**, not persisted separately from Chroma — `rag.py` reloads every document from Chroma on startup to rebuild it, which is fine at this corpus size (10–20 PDFs) but would need a persisted BM25 index at larger scale.
- **`MAX_IMAGES_PER_QUERY = 1`** — only one figure/table image is attached to the generation/grading prompts per query, even if multiple relevant visuals were retrieved. This keeps prompt size and latency predictable but means a question that genuinely needs two figures at once only gets the first.
- **No reranker.** Retrieval relies on RRF over dense + BM25 results; a cross-encoder reranker (e.g. `bge-reranker`) on the fused top-k would likely improve precision further, especially for corpora with more similar-sounding documents.
- **No streaming responses on `/ask`.** The endpoint returns the full answer after the whole graph completes (including verification), so response times reflect the full pipeline, not first-token latency.
- **Router misclassification risk.** The router is a single LLM call with no retry/confidence check — an ambiguously-phrased research question could occasionally be misrouted to `GENERAL` or `OUT_OF_SCOPE`.

## 8. What I'd improve with more time

- Add a cross-encoder reranker after RRF fusion.
- Persist the BM25 index alongside Chroma instead of rebuilding it in memory on every process start.
- Stream `/ask` responses (SSE) so the UI can show the answer as it's generated rather than waiting for verification to finish.
- Allow more than one image per query when multiple distinct visuals are relevant, with a token-budget-aware cap instead of a fixed count of 1.
- Add the evaluation harness (RAGAS / LLM-as-judge) to get a quantitative faithfulness/relevance score instead of relying on spot-checking answers manually.
